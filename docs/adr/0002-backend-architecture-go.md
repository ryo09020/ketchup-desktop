# ADR-0002: バックエンド API に Go (chi + pgx + oapi-codegen) を採用する理由

## ステータス
承認 (Accepted)

## コンテキスト
ユーザーは普段 Go と React を用いて Web アプリケーションを開発しています。
ketch-up (Web版) ではバックエンドとして TypeScript/Hono が使われていましたが、以下の理由からバックエンドを Go で統一・再構築することが求められました：
1. ユーザー自身の最も得意な言語が Go であり、長期的な保守・拡張が容易であること。
2. 将来的なクラウド展開（Cloud Run 等）において、コールドスタートが極小でメモリ消費が少なく、高スループットであること。
3. デスクトップアプリのローカルサイドカー（ローカル起動モード）としても、単一静的バイナリとして配布可能なこと。

## 比較検討した選択肢

| 項目 | Go (chi + pgx) | Node.js / Hono | Rust (Axum) | Python (FastAPI) |
|---|---|---|---|---|
| **ユーザーの習熟度** | ◎ 最も得意 | ◯ 経験あり | ✕ 習得ハードル高 | △ 経験少 |
| **起動速度 / コールドスタート** | ◎ 数ミリ秒 | ◯ 数百ミリ秒 | ◎ 数ミリ秒 | ✕ 数秒 |
| **メモリ使用量** | ◎ 15~30MB | △ 80~150MB | ◎ 10~20MB | ✕ 100~200MB |
| **APIスキーマ駆動** | ◎ oapi-codegen で完全自動生成 | ◯ Orval / HonoRPC | ◯ aide / openapi3 | ◎ FastAPI 自動生成 |
| **配布の容易さ (シングルバイナリ)** | ◎ CGO_ENABLED=0 で完結 | ✕ Nodeランタイム必要 | ◎ 完結 | ✕ 依存関係が複雑 |

## 決定
**Go 1.24+ (chi ルーター + pgx/v5 + oapi-codegen)** を採用します。

### 決定の論理的根拠
1. **スキーマ駆動開発 (Single Source of Truth)**
   `server/openapi/openapi.yaml` を定義し、Go 側は `oapi-codegen` でリクエスト/レスポンスの型とルーターインターフェースを自動生成します。フロントエンド (React) 側も同一の OpenAPI から型安全な API クライアントを生成するため、バックエンドとフロントエンドの型不整合がコンパイル時に検知されます。
2. **高い実行性能とリソース効率**
   `chi` は標準の `net/http` と 100% 互換でありながら、軽量かつ高速なルーティングを提供します。Postgres ドライバーには業界標準の `pgx/v5` を採用し、コネクションプールと効率的なクエリ実行を実現します。
3. **ローカル開発とクラウド運用の両立**
   ローカルでは Supabase やローカル Postgres に対して軽量に起動でき、本番では Google Cloud Run などのコンテナ環境に最軽量でデプロイ可能です。
